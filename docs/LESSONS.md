# 겪은 문제와 재발 방지

## L1. 버려진 위젯의 Tk 변수가 작업 스레드에서 해제됨 (2026-10-16)
- 증상: GUI 시험에서 `Exception ignored while calling deallocator Variable.__del__ … RuntimeError: main thread is not in main loop`.
- 원인: 언어·방법을 바꿀 때 지운 칩 위젯과 Tk 변수가 순환 참조(바인딩 람다 → ChipGroup → 칩)에 남아 있다가, 추정·미리보기 작업 스레드에서 돈 gc가 그 변수를 풀었다. 묶인 exe에서는 같은 일이 `Tcl_AsyncDelete` 중단으로 이어질 수 있다(scan-pdf-split 사례).
- 해결: 위젯을 지운 직후 주 스레드에서 `gc.collect()` (`gui._collect_now`) — `_build`, `_build_mode_widgets`, `_destroy`.
- 재발 방지: GUI 시험을 `-W error::pytest.PytestUnraisableExceptionWarning`로 돌려 0건 확인.

## L2. sv-ttk의 Toolbutton 라디오는 선택 상태가 안 보인다 (2026-10-16)
- 증상: 목표 용량 칩(200KB·500KB…)과 방법 버튼이 모두 같은 모양이라 무엇이 골라졌는지 알 수 없었다(캡처로 확인).
- 해결: `tk.Label`로 그린 `ChipGroup`(선택 = 강조색 바탕·흰 글자, 마우스 올리면 옅은 파랑).

## L3. 맑은 고딕이 Tk 글꼴 목록에 한글 이름으로만 있다 (2026-10-16)
- 증상: 한국어 화면 일부가 다른 글꼴로 그려짐. `tkfont.families()`에 `Malgun Gothic`이 없고 `맑은 고딕`만 있었다.
- 해결: 두 이름을 다 후보로(`theme.MALGUN`), sv-ttk·Tk의 이름 붙은 글꼴(`SunValley*`, `Tk*`) 모두에 같은 글꼴 지정.

## L4. 원본이 이미 목표보다 작을 때 (2026-10-16)
- 처음에는 품질 95로만 다시 저장해 원본보다 커지면 "이미 작음"으로 끝냈다 — 그러면 위치 정보가 남은 원본을 사용자가 그대로 올리게 된다.
- 해결: 목표 용량 모드의 실제 목표를 `min(목표, 원본 크기 - 1)`로 잡아, 원본보다 작은 결과(위치 정보 없음)를 가장 좋은 화질로 만든다. 그래도 원본보다 작게 못 만들면 그때만 "이미 작음".

## L5. 옆 패널이 최소 창 높이에서 잘림 (2026-10-16)
- 증상: 최소 크기(1000×680)에 새 버전 알림 줄이 붙으면 「투명한 PNG」 체크가 옆 패널 밖으로 밀렸다.
- 해결: 알림 줄을 왼쪽 열 맨 아래로(여전히 창 아래쪽), 「결과 위치」를 칩 한 줄로, 약속 문구를 미리보기 아래 한 줄로. 시험 `test_no_text_is_cut_off_at_the_smallest_window`가 알림을 띄운 채 `chk_png`·`btn_run`이 보이는지 본다.

## L6. pillow-heif 바이너리의 x265(GPLv2) (2026-10-16)
- pillow-heif Windows 휠의 libheif DLL은 libx265 DLL을 직접 불러온다(가져오기 표에 있음). 디코딩만 써도 빼면 로드가 안 된다.
- 처음 결과: 저장소 코드는 MIT, exe 전체는 GPLv2 조건. 사진 정리(photo-organizer) exe도 같은 처지.
- **해결(2026-10-16 사장님 결정, 허브 전달): 읽기 전용판 pi-heif로 교체.** pi-heif 1.4.0 휠에는 x265 DLL이 없고 libheif 가져오기 표에도 없다. 남는 libheif 1.23.0·libde265 1.1.1은 LGPL-3.0(휠의 LICENSES_bundled.txt는 1.18.1·1.0.15로 낡음 — 실행 중 `libheif_info()` 값을 믿을 것). pillow-heif는 시험용 HEIC 샘플을 **쓰는 데만** 쓰고, Pillow 플러그인으로 등록하지 않는다(등록하면 시험이 pi-heif가 아니라 pillow-heif로 읽어 증명이 안 된다). `shrink.register_heif`는 부를 때마다 여는 쪽이 pi-heif인지 확인한다. 증명: `tests/test_heic_reader.py`(같은 픽셀·EXIF·ICC·결과 바이트, 10비트 포함, 새 프로세스에서 pillow_heif 미적재).

## L8. 실제 사진(사본)에서 찾은 것 (2026-10-16)
사장님 지시로 사장님 PC의 Windows 「사진」 폴더(349장)를 **스크래치패드에 복사해서** 6가지 방법으로 돌렸다(원본 폴더는 전·후 SHA-1 비교로 그대로임을 확인).
- **Windows 화면 캡처 PNG는 투명한 곳이 없어도 RGBA다.** 형식(모드)만 보고 「투명한 PNG는 PNG로」를 적용해 279장이 전부 PNG로 남았다(줄어듦 40%, 177초). 해결: 계획 때는 .jpg/.png 이름을 둘 다 잡아 두고, 픽셀을 읽은 뒤 알파가 255보다 작은 픽셀이 있을 때만 PNG(`final_format`). → 72%, 17초.
- **PNG 압축 단계 9는 6보다 10배 느리고 9%만 작다.** 탐색은 단계 6, 고른 크기에서 마지막 한 번만 9(더 작을 때만 채택).
- 점검이 도는 동안 Windows가 `Screenshots`에 새 캡처를 저장해 원본 파일 수가 늘었다. 원본 비교는 "원래 있던 파일이 그대로인가"와 "새 파일이 도구 산출물인가"로 나눠 본다.
- 사본의 `Camera Roll`은 읽기 전용 속성까지 복사돼 `rmtree`가 막힌다(지울 때 속성을 풀 것).

## L9. 창을 닫은 뒤 깨어나는 예약 호출 (2026-10-16)
- 증상: 점검 하네스에서 창을 닫은 직후 `invalid command name "…_poll"`.
- 원인: `root.destroy()`가 tkinter 명령을 지워도 Tk의 `after` 대기열에 `_poll`이 남는다. 닫은 뒤 이벤트를 한 번 더 처리하면(하네스, 같은 단계에 만료된 타이머) 깨어나 오류.
- 해결: `_destroy`에서 대기 중인 `after`를 취소(루트가 Tk면 전부, Toplevel이면 이 App 것만).
- 재발 방지: `test_a_real_run_then_close_leaves_no_tcl_errors` — 별도 프로세스에서 실행·닫기 뒤 `update()`를 한 번 더 하고 stderr가 비었는지 본다(수정 전 코드로 실패 확인함).

## L10. 예상 크기가 실제와 크게 달랐다 (2026-10-16)
- 증상: 실제 사진 사본 349장(대부분 화면 캡처)에서 예상 99.1MB, 실제 64.1MB(+55%).
- 원인: 앞 3장만 줄여 보고, 목표 용량 모드에서는 나머지를 "원본과 목표 중 작은 값"으로 짐작했다. 목표보다 작은 캡처 PNG도 JPG가 되며 크게 줄어드는데 그걸 그대로로 봤다. 표본을 늘려도 평균·중앙값·가장 가까운 표본은 글자 위주냐 사진 위주냐에 따라 −81%~+588%로 흔들렸다(측정표는 이 세션 기록).
- 해결: ① 표본을 파일 형식·크기에 고루(`sample_indices`), ② 짐작은 형식별 로그-로그 직선(`guess_sizes`), ③ **점점 정확해지는 추정**(`estimate_iter`): 3장 → 12장 → 나머지를 백그라운드에서 메모리 안에서만 줄여 1초마다 갱신, 400장까지. 다 재면 정확히 0% 오차("모든 사진을 실제로 줄여 본 크기"). [줄이기]·옵션 변경·목록 비우기 때 멈춘다.
- 함께 찾은 결함: 「목록 비우기」가 돌던 추정을 멈추지 않아 빈 목록에 옛 숫자가 들어왔다(`test_clear_while_estimating`).

## L11. 다른 세션의 GUI 시험과 동시에 돌리면 Tk가 수십 초 멈춘다 (2026-10-26)
- 증상: 「의견 보내기」 시험 중 새 창을 띄운 뒤 첫 `root.update()`가 54초 걸려 시험이 멈춘 것처럼 보였다. 바꾸기 전 코드(`git archive HEAD` 사본)로도 같은 시각에 똑같이 멈췄다.
- 원인(추정): 같은 PC에서 다른 책갈피 툴 세션 8개 안팎이 pytest·GUI 캡처를 동시에 돌리고 있었다. 프로파일에서 시간은 전부 Tk 내부 호출(`tkapp.call`)이었고 파이썬 콜백은 몇 번뿐이었다. 다른 프로그램이 끝난 뒤 같은 시험은 그대로 통과했다.
- 재발 방지: 시험이 멈추면 먼저 `Get-Process python`으로 다른 세션의 pytest·GUI가 도는지 보고, 원래 코드 사본으로 같은 시험을 돌려 비교한다. 코드 탓으로 단정하기 전에 `faulthandler.dump_traceback_later`로 어디서 멈췄는지 본다.
- 같은 날 `test_add_estimate_run_summary`가 3.14·3.12 모두, 따로 돌려도, 바꾸기 전 코드로도 실패했다. 창을 만들고 첫 `update()`까지 약 5초 걸리는 사이 추정이 3장 → 7장 다 끝나, 두 결과를 한 번에 꺼내 "약(about)" 중간 숫자가 화면에 나오지 않았다(시험이 중간 상태를 기다린다). 프로그램 동작은 맞다(바로 정확한 숫자). 시험을 고치는 일은 「의견 보내기」 범위 밖이라 허브에 보고만 했다.
- 함께 한 일: conftest가 `webbrowser.open`도 막는다(기록하고 "열림"으로 답함). 가짜를 깜빡한 시험은 메시지 상자에 걸리지 않고 실패로 드러난다.
